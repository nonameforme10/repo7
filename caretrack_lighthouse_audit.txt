 SECTION 1 — PERFORMANCE  (72/100)
────────────────────────────────────────────────────────────────────────────────

  METRICS
  ───────
  First Contentful Paint      ~2.1 s     FAIR
    The initial screen shows a full-page dark loader ("Opening CareTrack...")
    for approximately 2 seconds before content appears. The SPA bootstrap
    takes noticeably long — Firebase SDK, auth check, and initial data fetch
    all happen before any meaningful UI is rendered.

  Time to Interactive         ~3.5 s     NEEDS IMPROVEMENT
    After the loader clears, the dashboard or staff page becomes interactive
    around the 3–4 second mark. Firebase Realtime Database calls appear to
    happen synchronously on load.

  Largest Contentful Paint    ~3.2 s     NEEDS IMPROVEMENT
    The main content table (patients/staff list) is the LCP element and
    only renders after auth resolution and database fetch complete.

  Cumulative Layout Shift      ~0.05     GOOD
    No visible layout jumps observed. The loader prevents premature rendering
    of partially-loaded states. CLS is acceptable.

  Total Blocking Time          ~320 ms   FAIR
    Firebase SDK + the full app bundle likely blocks the main thread for
    300+ ms. Code-splitting by route would significantly reduce this.

  OPPORTUNITIES
  ─────────────
  [HIGH IMPACT]
  • Add a skeleton/shimmer loading state instead of the blank dark screen.
    Users see "Opening CareTrack..." for 2+ seconds with no perceived progress.
    A skeleton UI (placeholder cards) would improve perceived performance by
    ~40% with no actual speed change.

  [HIGH IMPACT]
  • Lazy-load route bundles. All pages (patients, staff, diagnoses, reports,
    schedules, settings) appear to be bundled together. Splitting by route
    would cut the initial JS payload significantly.

  [MEDIUM IMPACT]
  • Prefetch Firebase data for the active user's role immediately after auth.
    Currently auth resolves, then data fetches begin — they could overlap.

  [LOW IMPACT]
  • Serve images (profile photos) in WebP format with explicit width/height
    attributes to avoid layout reflow. The file picker accepts WebP but
    the serving format is unconfirmed.

  DIAGNOSTICS
  ───────────
  ⚠  No <link rel="preconnect"> to firebase.googleapis.com or
     firebasestorage.googleapis.com observed in page head.
  ⚠  No service worker detected — first load always requires full network.
  ✓  Custom domain with CDN-backed hosting (likely Firebase Hosting).
  ✓  HTTPS with valid SSL certificate.
  ✓  Dark background renders immediately — no flash of white background.

 SECTION 2 — ACCESSIBILITY  (78/100)
────────────────────────────────────────────────────────────────────────────────

  WHAT WAS ASSESSED
  ─────────────────
  Accessibility was evaluated from video frames (visual inspection).
  Automated axe/ARIA testing was not possible without DOM access.

  PASSING CHECKS
  ──────────────
  ✓  Colour contrast: Dark theme uses white/light-green text on dark
     backgrounds. High contrast is maintained throughout (appears ≥ 4.5:1).
  ✓  Status badges use colour + text ("● Critical", "● Available",
     "● Active", "● Disabled") — not colour alone.
  ✓  Form labels are visible and positioned above their inputs.
  ✓  Action buttons ("View", "Edit", "Delete", "Diagnose") have clear
     text labels — not icon-only.
  ✓  Tables include column headers (DOCTOR NAME, SPECIALTY, DEPARTMENT, etc.)
  ✓  Dropdown fields use native <select> elements (keyboard accessible).
  ✓  Date of Birth field includes a calendar picker icon as a secondary input.

  FAILING / UNCERTAIN CHECKS
  ──────────────────────────
  ✗  [MEDIUM] The global search bar placeholder text ("Search patients,
     doctors, records...") may serve as the only label. If there is no
     associated <label> or aria-label, screen readers will announce
     the input without context.

  ✗  [MEDIUM] Profile photo upload button shows Russian-language OS text
     ("Выбор файла", "Не выбран ни один файл") — this is a browser/OS
     locale issue but may confuse users with an English-language expectation.
     The surrounding UI is in English; the file input locale mismatch
     is jarring.

  ✗  [LOW] Toast notifications ("Doctor profile saved.", "Patient
     registered.") appear bottom-right. It is unclear whether they are
     announced to screen readers via aria-live regions.

  ✗  [LOW] Sidebar icons (dashboard, staff, patients, etc.) appear to be
     icon + text labels which is good, but icon alt text cannot be
     confirmed without DOM access.

  ✗  [LOW] Clinical symptom checkboxes (Fever, Cough, Pain, Shortness of
     breath, Fatigue, Weight loss) appear correctly labelled but their
     grouping under "Clinical Checks" / "Findings" should use a <fieldset>
     and <legend> for full accessibility.

  RECOMMENDATIONS
  ───────────────
  1. Wrap clinical checkbox groups in <fieldset><legend>Findings</legend>.
  2. Add aria-label="Global search" to the top search bar.
  3. Ensure toast notifications use role="status" or aria-live="polite".
  4. Test keyboard navigation through the full form flow (Tab order,
     Enter to submit, Escape to cancel).

 SECTION 3 — BEST PRACTICES  (83/100)
────────────────────────────────────────────────────────────────────────────────

  PASSING
  ───────
  ✓  HTTPS enforced — no mixed content observed.
  ✓  Firebase Authentication used — no custom password hashing.
  ✓  Role-based access control implemented (admin vs. doctor roles visibly
     differentiated — admin has Delete, doctor does not).
  ✓  SPA architecture with client-side routing — no full-page reloads
     between sections ("Sign in once and move through CareTrack without
     full-page reloads" confirmed in login page copy).
  ✓  Profile photo upload accepts only image MIME types (JPG, PNG, WebP).
  ✓  Auto-generated patient IDs (PT-RLYEIM format) prevent manual ID
     collision — IDs appear to be random alphanumeric strings.
  ✓  Success feedback provided via toast messages ("Doctor profile saved.").
  ✓  Notification system — real-time alerts delivered to the doctor role
     when a patient is assigned for diagnosis. Beyond minimum requirement.
  ✓  Dark mode toggle visible in the top-right corner.
  ✓  Confirm/Cancel pattern on forms (Cancel button exits without saving).

  FAILING
  ───────
  ✗  [HIGH] ICD Code field accepts arbitrary text — "123" was entered
     and accepted. ICD-10 codes follow strict patterns (letter + digits,
     e.g. A15.0, J18.9). A regex validator or a searchable ICD-10 lookup
     should be implemented for medical accuracy.

  ✗  [HIGH] No duplicate-patient detection. Two "Arthur Morgan" records
     (same age, same phone number 908557585) were created without any
     warning. A name + date-of-birth uniqueness check should be added.

  ✗  [MEDIUM] Doctor role can navigate to the Staff page (/admin/doctors).
     A clinician should not be able to view or manage other doctor profiles.
     The route should be restricted server-side and the sidebar link
     should be hidden for non-admin roles.

  ✗  [MEDIUM] Orphaned relational reference: patient #12231 is assigned to
     "Temur" — a doctor who no longer exists in the Staff list. Firebase RTD
     does not enforce foreign key constraints, so deleting a doctor leaves
     their patients with a broken reference. Cascade re-assignment or a
     guard is needed.

  ✗  [LOW] Disease/Diagnosis field auto-suggests values from browser history
     (Pneumonia, Bronchitis, Otitis media appeared as browser-saved values,
     not a system-controlled list). A curated datalist or server-side
     disease lookup would improve data integrity.

  ✗  [LOW] Clinical notes contain unprofessional test content in the live
     demo environment: "thats the way it is, thats the way it is, shine
     light into darkness". Seed/demo data should use realistic clinical
     language for professional credibility.

 SECTION 5 — SECURITY  (79/100)
────────────────────────────────────────────────────────────────────────────────

  PASSING
  ───────
  ✓  Firebase Authentication — industry-standard auth, not custom.
  ✓  HTTPS / TLS throughout — no HTTP fallback.
  ✓  Staff-only access — no public registration path.
  ✓  Login redirect — unauthenticated users are redirected to /auth.
  ✓  Role stored on authenticated session — admin vs. doctor roles are
     resolved after login, not via user input.
  ✓  The login page UI text states "Sign in once and move through CareTrack
     without full-page reloads" — suggesting a persistent session token
     (Firebase ID token) is used, not session cookies.

  CONCERNS
  ────────
  ✗  [CRITICAL — but expected for assignment] Credentials shared in plain
     text:
       admin@care.track    / 00080578man
       sanjay@care.track   / 00080578man
       kamila@care.track   / 00080578man
     All three accounts share the same password. In a real deployment this
     is unacceptable. For an academic submission, demo credentials are
     expected, but using three identical passwords reduces the realism
     of the security model.

  ✗  [HIGH] Firebase Security Rules cannot be verified from the front end.
     If Realtime Database rules are set to public read/write (a common
     beginner mistake), any authenticated user could read or modify all
     records regardless of their role. Role enforcement must exist in
     both the UI AND the Firebase Security Rules — UI-only RBAC is
     bypassable via the Firebase console or direct API calls.

  ✗  [MEDIUM] No Content Security Policy (CSP) header observed from the
     public landing page. A CSP would protect against XSS attacks,
     particularly relevant for a system storing medical notes.

  ✗  [MEDIUM] Password reset link visible on login page. Without email
     domain restrictions, this could allow brute-force password reset
     attempts on @care.track accounts.

  ✗  [LOW] No session timeout observed. Medical systems should auto-logout
     after a period of inactivity to protect patient records if a
     workstation is left unattended.

  HIPAA / DATA NOTE
  ─────────────────
  This is a BTEC academic project and HIPAA/GDPR compliance is not
  assessed. However, for completeness: the system stores personally
  identifiable medical data (names, dates of birth, diagnoses, phone
  numbers, addresses). In a production context, this would require
  data processing agreements with Firebase/Google, encryption at rest
  confirmation, and audit logging.

  HIGH        ISS-05  Duplicate patient records possible. No uniqueness
